New features that are still being tried out start off, with a switch under
`experiments` in `runner.json` (the user guide, "Experiments", says how to turn one
on). These are the ones there are now.

## What each one does

<!-- list:start -->
- **External messages in Backlog** (`externalIntake`, since 8 Nov 2026). Every 15 seconds while sync is running, save received messages from explicitly bound intake clients as unsent Backlog drafts. Their original text stays in the composer; Message source in Highlights holds provenance. No task session, turn or worktree starts until you send the draft. Existing Backlog librarian review may add context. Retries, restarts and deletion do not create the same task again. With backend API 66, attachments are transferred in private blocks, verified and saved locally with the complete draft. Cloud bytes are removed only after durable local confirmation. Pending data has no age expiry. See docs/intake.md for checksum holds and storage lifecycle. Sender receipts continue to mean received by Convex. Known test messages must be explicitly excluded before binding a production client. Off by default; turning it off takes effect on the next poll and does not delete existing drafts.
- **Recap box on quiet threads** (`recapBox`, since 10 Nov 2026). When you open a thread that hasn't done anything for 12 hours or more, a box above the message box says what the thread is for and where it stands, so you don't have to ask. The librarian writes it ahead of time, after each turn, as part of the look it already takes, so it costs no extra model calls. Press × to put it away; sending a message does too. It shows on the Mac, the phone and the website.
- **Nested threads** (`nestedThreads`, since 15 Nov 2026). Threads another thread started sit indented under it in the sidebar, like sub-agents, instead of having rows of their own across the inbox. The group sits where its most urgent member would: in the inbox if any of them needs you, in Running if any is working, otherwise where the starting thread is. It opens by itself when one of them has a question for you and folds otherwise, saying how many are working. Each one opens with a line saying which thread started it and why. An agent can start a thread that isn't part of its work as one of its own, and you can move a thread out from under its starter, or back, from its menu. The starting thread no longer wakes for each report its threads send it: they're kept until all of them have finished (or one fails), then come to it together. Mac app only for now.
- **Shared memory** (`sharedMemory`, since 17 Nov 2026). A thread on your main Mac knows you mostly from what Claude Code loads before your first message: your global `CLAUDE.md`, and the memory folder of the project it's in (`MEMORY.md` and the notes agents save as they learn things). Without this, those stay on the main Mac, so a thread on another runner starts knowing nothing about you. With it on, the main Mac puts them up to your backend every minute, and each other runner copies them into its own Claude logins (and the global file into Codex's `AGENTS.md`), under its own home folder: `~/dev/me/misc`'s memory on the main Mac becomes `~/dev/me/misc`'s on the other runner too. Only folders under your home folder go, not `~/Library`. A file that was on the other runner before sync wrote it is left alone. When an agent on another runner saves a memory, or changes one the main Mac sent, it's sent back as an offer, not written into the main Mac's memory (its own edit stays there until the main Mac has a newer version): offers land in `memory-offers/<runner>/` in the main Mac's data dir, for you or a scheduled job to fold in or drop. Another runner's key can't change what the main Mac's agents read. Secret values the runner knows of are masked before anything goes up. Turn it on on every runner (`"experiments": { "sharedMemory": true }` in runner.json): the main Mac to put its files up, the others to take them.
- **Inbox guess** (`inboxGuess`, since 18 Nov 2026). Finds out which finished threads you didn't need to see, without hiding any. On the done card, Archive opens a small menu: "Didn't need this" (the agent only did what you'd told it to, and the thread could have gone straight to Archived), "Glad I saw this", or "Not sure" for the in-between ones, which is kept but not scored. Each archives the thread as before, and leaves a line in it saying which you picked. ⌘E, a row's archive button and a swipe still archive straight off, with no menu. Meanwhile, each time one of your own threads finishes with nothing for you, two models (a cheap one and a strong one) each guess whether you needed to see it, from your last message to it and the agent's reply. A thread that suggested follow-ups or left anything open always counts as one to see, with no model asked. The guess does nothing and shows nowhere: the thread stays in your inbox either way. The guesses and your picks are written to `inbox-guess.jsonl` in the runner's data folder, so you can see how often a model would have been right before letting it archive anything. Threads in a private folder aren't sent to a model. Threads on another runner, and archives from the phone or the website, aren't part of it yet.
- **Live pages** (`livePages`, since 19 Nov 2026). An agent can show you something that moves or that you can turn around (a 3D model, an animation, a small simulation) as a live page: one self-contained HTML file it puts in its reply like a picture, `![Garden lights](/path/garden.html)`. The thread shows it as a card with Run, on the Mac and on the iPhone (it goes up the way pictures in replies do, at most 10 MB; the Android app and the website don't run them yet). Run starts it there in the card, for that version of the page; on the Mac it shows while the whole card is in view. It stays sealed off: it can't reach the internet or read any file but its own, and it can't open anything. A page an agent only pins stays on the Mac.
- **Virtual runners** (`virtualRunners`, since 19 Nov 2026). Runs on in the new-thread box lists your virtual runners after your Macs, for example Cloud (Fly): a thread started there gets a box of its own in the cloud, which clones the folder's repo and runs Claude Code there, sleeps when the thread's idle and wakes for its next message. The first time a thread runs on one with a Claude login that has no cloud token, the thread shows a card: Make one runs `claude setup-token` for that login and opens claude.ai to approve it, or paste one, or use that login's year-long token from this Mac. The message waits and goes once the token's set, and the card comes back if Claude ever refuses the token. A virtual runner has to be set up in your Convex backend first (docs/virtual-runners.md).
- **Agent Archive** (`archive`, since 20 Nov 2026). For people running Agent Archive, Mike's archive of every agent conversation, which isn't public yet: without it installed, this only keeps a list. Every ten minutes the runner writes `archive-sessions.json` in its data folder, saying which Claude or Codex session belongs to which Threadbear thread, with the thread's title, project and folder, and where each of your Claude and Codex logins keeps its sessions, so a login you add is archived too. Agent Archive's sync reads that list and sends it to the archive with its own credentials, so search results and the archive's reader can open the thread in Threadbear. The runner also reads the sync's state for `tb status` and says when it has stopped, and asks the archive server it syncs to how it is (`/api/health`): whether it answers, and any failed deploy or backup or low disk. On the server's own machine, a server that has stopped and that launchd hasn't started again is started. When runner.json's `archive.repo` names the archive's git repo, the runner builds the sync from its main whenever main moves and installs it with the archive's own installer, then on the machines in `archive.pushTo` over ssh. A machine running the archive server leaves that to the server's own deployer. With Agent Archive installed, the app's thread search also searches the archive, after your threads: every word said anywhere in a session, sessions run outside Threadbear, and every machine that syncs to it. A result opens read-only in the thread's place, with New thread from this to pick it back up. Every thread's agent gets the archive's own tools, even on a login whose config doesn't list them. The sync stays a background service of its own, so the runner restarting never stops it mid-upload. The plan for the rest is in docs/agent-archive-plan.md.
- **Email watcher** (`mailWatch`, since 20 Nov 2026). Every few minutes the runner runs a command of yours that prints your new emails, and a small model sorts them against your threads. An email a hibernating thread was waiting on (a reply, an approval, a delivery) wakes that thread with the email, and its agent checks it really is what it waited for. An email about an open thread's work is kept for that thread: a note in it says so, and its agent reads the email on the thread's next turn, without one being started for it. When one of your standing decisions (files you name, such as a memory index) clearly says what to do with an email, and a stronger model agrees, it's done straight away in the thread it belongs to or a new one, which archives itself when finished; at most four a day, and never sending, posting, paying or deleting unless the decision says exactly that. Anything else that looks like it needs you goes on a list, which comes as one thread at 9 am and 4 pm (or the times you set), with a suggested action for each and what was done without asking since the last one. Where an email only says something needs you and not what (an order on hold, say), the list's agent finds out on that service's own site first, so its question says what's wrong. Newsletters, receipts and notifications are left alone. Only the main Mac's runner looks. It needs `mailWatch` in runner.json: `command` (prints a JSON list of emails, each with `id`, `from`, `subject` and the start of its `text`, and optionally `account`, `date`, `url` and `threadId`; it gets `THREADBEAR_MAIL_STATE`, a file it may keep its place in), and optionally `everyMinutes` (5), `digestAt` (`["09:00", "16:00"]`), `folder` (where new threads start; your home folder), `decisions` (files of standing decisions; none means it never acts) and `act: false` to never act. The runner holds no mail login: the command reads the mail. The sender, subject and first 1,500 characters of each new email go to the model, with your recent threads' titles and briefs (never a private folder's).
- **Recipes** (`recipes`, since 20 Nov 2026). A Recipes view on the left (the book in the rail) lists extra routines and ways of working you can choose, such as a short morning brief, a nightly look back at what you had to correct, a weekly step back, a standup draft, or the email watcher. What every agent should do to use Threadbear well is built in instead, not a recipe. Each has a card with its picture, what it does and how often it has run. Open one to see what it's for, a made-up example of a run, what it set up, its runs over the last 30 days and a log of them. Add starts a thread in the recipe's own folder where an agent sets it up with you, around the tools and connectors you have, and makes its schedule; from then on its switch pauses and resumes that schedule (for one that's an experiment, such as the email watcher, the switch is the experiment's). Remove deletes what it set up. A recipe can also be a habit, a way of working rather than a job, such as "show me a few options": while it's on, every thread's agent is told its few lines, beside your standing instructions, with nothing written to your CLAUDE.md or AGENTS.md. Add switches a habit on straight away with no setup, its page shows the exact words and what they add to each thread, and if its file changes later you choose when agents get the new wording. New recipe starts a thread that writes one with you, with a header picture if the agent can make one; Change it with an agent changes one (a copy, for one that comes with Threadbear). Your own recipes, and the working files of set-up ones, are in `~/ThreadbearThreads/recipes` (`"recipes": { "folder": "..." }` in runner.json to change it). The format is `runner/src/recipes/FORMAT.md`. Desktop (GPUI) app only.
- **End turn up front** (`loadEndTurn`, since 21 Nov 2026). Claude Code keeps MCP tools out of a session until the agent looks them up with its tool search, so a fresh Claude thread spent its first step just loading end_turn, sending the whole conversation again to do it. With this on, end_turn is part of every request from the start, so that step goes. A "hello" in a new thread takes 2 requests instead of 3 (about a third fewer tokens, and the first reply arrives one round trip sooner). The other Threadbear tools still load when they're needed. Claude only: Codex lists every tool anyway.
- **Review canvas** (`reviewCanvas`, since 22 Nov 2026). A design review's window becomes a board you drag around and zoom into, with every picture laid out on it: each option's pages in a column under its name, on a faint glow with its big letter behind, the glow turning green and its pictures ringed once you tick it. The agent can draw on any of its pictures in a handwritten style: circles, underlines, marker swipes and curled arrows, each with a few words beside it, in colours with jobs (yellow points something out, green is what solves it, rose is a cost). A switch hides them when you want the pictures clean, and a tour flies from picture to picture. Tools of your own circle, highlight or pin a part of any picture: each drops a numbered chip into your reply, so you can say "[Mark 1] is too tight", and the agent gets a cut-out of that part with your answer. A clip, a sound or a page plays where it sits on the board: press Play on it, or double-click it.
- **Quiet inbox for your threads** (`quietInboxMine`, since 23 Nov 2026). Part of the quiet inbox. Threads another thread started already archive themselves when they finish with nothing for you; this does the same for your own threads, when a model is confident you didn't need to read the reply. It needs Inbox guess on too, as the guess comes from there: when one of your threads finishes with nothing for you and nothing left open, the strong model (Opus) guesses whether you needed to see it. If it says no, the thread is archived with a line in it saying why. A thread with follow-ups, anything left open, a star, one you've already looked at, or one you once brought back out of the archive is never archived this way, and nothing happens if Opus couldn't answer. To check what it hid, a daily thread (a schedule of Mike's, while the experiment runs) lists the threads it archived the day before, with the model's reason for each. Tell it which you should have seen: it brings them back with `tb unarchive <id> --wrong-hide`, which writes the miss down so the guess can be scored. Or right-click an archived thread and pick Should Have Shown Me, which does the same. (A "Quietly archived: N today" line at the foot of the Inbox did this for a day; Mike didn't want it cluttering the sidebar.) The decisions and your corrections are in `inbox-guess.jsonl` in the runner's data folder. Threads on another runner aren't part of it yet.
- **Canvas** (`threadCanvas`, since 24 Nov 2026). A Canvas button in the rail (three windows joined by arrows) opens a board in place of the thread list and the thread, with every live thread on it as a small copy of its window: its title with the amber dot while it waits on you, what you last asked, the agent's latest words and its question, and the message box. Each project is an area with a fixed place and its name faint above it, the biggest on the left; threads in no project are in Loose. Inside an area threads grow left to right, with a curved arrow from each thread to the ones it started, labelled in handwriting with why. A new thread grows in beside the thread that started it, or at its area's open edge, its area glows for a moment, and nothing else moves. An archived thread shrinks to a faint pill that keeps its arrows, and the pills go once their whole tree is archived (after an hour and a half), or when you press Tidy, which also closes the gaps. Threads a schedule, a tool or Threadbear started on their own wait in a strip along the bottom, and move onto their area only once they need you. Click a project's name to fade the others back; Esc or a click on the empty board brings them back. ⌘ or Control with the wheel, or a pinch, zooms round the pointer; the wheel or two fingers move the board, and you can drag a thread's window to another place, where it stays. Click a thread and the board flies in until it fills the view, and the real thread takes over there: the wheel scrolls it and the message box works. ⌘ and the wheel toward you, a pinch out, Esc or a click beside it flies back out. Where everything sits is kept between launches. Mac and the other desktops (the GPUI app) only.

## Adding one, and ending one

For agents adding a feature (AGENTS.md, "Experiments"). A new feature the owner of the copy is
still trying out lands off by default and on for them. Bug fixes and polish go straight in: an
experiment is for new behaviour that changes what threads do, what they cost, or what the
runner does to the machine.

- Give it a file of its own, `runner/src/experiments/<id>.md` (copy one that's there): its
  id, name, title, `added` date, `on: false` and `reminder`, then what it does (for the
  guide), where it lives and how to take it out (for forks). Check
  `experimentOn(home, '<id>')` where it starts. Put `"experiments": { "<id>": true }` in the
  owner's `runner.json` (`~/Library/Application Support/Threadbear/runner.json`) so it's on
  for them. Settings > General > Experiments lists it by itself, with its name and "What it
  does" behind the ⓘ (`settings.update`'s `experiments`), so write those for the people
  flipping it.
- Run `npm run experiment-docs` in `runner/` and commit this file with it;
  `experiment-docs.test.ts` fails while it's out of date. Edit the experiment's file, never
  this one. One file each and a line-by-line merge here (`scripts/merge-lines.mjs`) mean two
  threads adding or taking out experiments at once don't collide.
- Book the check-in when it lands: `schedule_message` with `new_thread` in this repo, about
  four days out, telling that thread to look at how the experiment has gone and ask the owner
  whether to turn it on for everyone, keep trying it, or take it out. Its id is the file's
  `reminder`; `experiments.test.ts` fails without one.
- To make it standard, take the flag out entirely: its file, the `experimentOn` check, its
  key in every runner.json that has it (each machine with a runner), then
  `npm run experiment-docs`. Its "What it does" text moves to where the feature belongs in the
  guide. Don't leave a default-on switch behind: every flag left in is another path through
  the code to keep working. If people might really want it off, make it a normal setting
  instead. To take it out, delete the feature with its flag.
